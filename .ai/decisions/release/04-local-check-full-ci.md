# 本地快速反馈，所有 CI 保留完整验证

最后更新：2026-10-19

状态：已接受
模块：release
日期：2026-10-19
来源：已确认的本地验证范围、`scripts/tasks.mjs`、`scripts/test-suites.mjs`、`.github/workflows/ci.yml`

背景：频繁执行浏览器、文档双路径构建、隔离安装及批量示例编译，使本地改动的反馈周期过长。仅凭 Node 文件后缀无法划分成本：有些 Node 用例仍会启动 Chromium 或真实开发服务器。

决策：日常本地验证以快速反馈为目标；所有 PR 与主分支 CI 保留完整验证。测试编写原则与执行时机由 `TESTING.md` 统一维护；套件发现约束与验证结构见[交付结构](../../architectures/release/delivery-pipelines.md#ci-质量门禁)，各阶段命令以 `scripts/tasks.mjs` 为准。

理由：本地快速反馈与合并前验收有不同频率和成本。把高成本验证留在所有 CI 中，可以保留合并前保护，同时避免每轮编辑都重复隔离安装与浏览器矩阵。用户最终要求 PR 也执行全量验证，因此不采用仅主分支执行完整验证的方案。

代价：本地通过不能证明真实点击、焦点、布局及独立安装正确；提交 PR 后仍可能发现这些缺陷。SSR 仍需准备当前公开包，不能依赖旧产物来隐藏耗时。完整 CI 的运行成本继续存在。

重新审视条件：本地实测仍无法提供足够快的反馈；快速组加入了浏览器或重型集成行为；或完整 CI 的反馈成本需要单独优化。任何进一步裁剪都必须说明由什么验证继续承担原有风险。
